# Обновления PDFx

Механизм перенесён из Papka (репозиторий `Aev199/filemanager`) и
приспособлен к тому, что переносной PDFx — папка с файлами, а не один EXE.

## Выпуск новой версии

Выпуск собирается в GitHub Actions; файл `release.yml` должен лежать в
ветке по умолчанию, иначе кнопки «Run workflow» не будет.

1. GitHub → Actions → **Release** → Run workflow.
2. Поля запуска:
   - **channel**: `beta` — тестовая сборка (её получают только те, у кого
     в настройках выбран канал «All builds (beta)»); `stable` — для всех.
   - **publish**: снять флажок, если нужна только сборка без выпуска
     (ZIP останется в артефактах запуска).
   - **notes**: что нового, пункты через `;`. Пусто — берутся заголовки
     коммитов с прошлого выпуска.
3. Сборка получает версию `1.0.<номер запуска>`, проходит проверку типов,
   юнит-тесты, сквозные сценарии и проверку замены папки на Windows и
   публикует выпуск `v1.0.N` с файлами `PDFx-Windows-Portable.zip` и
   `latest.json` (версия, коммит, канал, SHA-256 архива, список изменений).

Бета-выпуск можно сделать стабильным позже: на странице выпуска снять
отметку «Set as a pre-release».

## Как обновляется программа

- Через 8 секунд после запуска и затем раз в сутки (если не выключено в
  Settings → Updates), а также по Help → Check for Updates PDFx
  запрашивает список выпусков GitHub. Запрос идёт сетевым стеком Chromium —
  через системный прокси, как в браузере. Нет сети — фоновая проверка
  молча пропускается.
- Найденная версия появляется значком «Update 1.0.N» в строке вкладок.
  Можно обновить, отложить или пропустить версию.
- Загруженный ZIP сверяется с SHA-256 из `latest.json` и распаковывается в
  `data\updates\staged`. Проверяется, что в нём есть `pdfx.exe`,
  `resources\app.asar` и `version.json` с ожидаемой версией.
- Работающую программу заменить нельзя, поэтому замена происходит после
  закрытия: при «Restart now» или при обычном закрытии PDFx запускается
  скрытый PowerShell-сценарий. Он ждёт завершения PDFx, переносит текущие
  файлы программы в `data\updates\previous`, а новые — на их место.
  Переносятся только файлы, которые есть в новой версии: `data` и чужие
  файлы рядом с `pdfx.exe` (ZIP без корневой папки могли распаковать прямо
  в «Загрузки») не трогаются. Перенос идёт в пределах одного диска, поэтому это быстрые
  переименования. При ошибке на любом шаге всё возвращается как было.
- При следующем запуске PDFx сообщает, установилась ли новая версия.
  Сеанс (вкладки, пометки) сохраняется перед закрытием, как обычно.
- About → «Back to version …» возвращает предыдущую версию тем же
  способом; отменённую версию потом можно вернуть ещё раз.
- Сборки, сделанные не через Release (`dev`, `ci`), сами не обновляются.
- Если в папку программы нельзя писать (например, она лежит в Program
  Files или на сетевом диске только для чтения), PDFx предлагает скачать
  новую версию со страницы выпуска и распаковать её вручную.

## Если программе закрыт интернет (брандмауэр пускает только браузер)

- Проверка по кнопке показывает «GitHub is out of reach» и кнопку
  «Download in browser»: браузер скачивает `PDFx-Windows-Portable.zip` в
  «Загрузки» — на стабильном канале из последнего стабильного выпуска, на
  бета-канале самую свежую сборку.
- PDFx 20 минут следит за «Загрузками» (и проверяет их раз в час) и
  предлагает установить найденный архив. Версия читается из `version.json`
  внутри ZIP, «PDFx-Windows-Portable (1).zip» тоже подходит.
- У GitHub постоянная ссылка `releases/latest` ведёт только на стабильный
  выпуск, поэтому каждая публикация ещё кладёт ZIP в отдельный выпуск с
  тегом `beta` («PDFx: последняя сборка»). В нём нет `latest.json`, и PDFx
  не предлагает его как обновление.

## Для проверок

Переменная окружения `PDFX_UPDATE_FEED=<папка>` заставляет PDFx брать
`latest.json` и `PDFx-Windows-Portable.zip` из этой папки вместо GitHub
(так работает сквозной тест). Замену папки при этом PDFx не выполняет:
её проверяет отдельный сценарий `scripts/test-update-apply.ps1` на
настоящей сборке в Windows CI.
